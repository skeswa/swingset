# SQLite schema history

The Postgres port starts at schema 37 and applies migrations explicitly through
[`postgres_schema.py`](../../src/swingset/state/postgres_schema.py). Original
SQLite SQL and upgrade assertions are preserved in the
[checksummed historical fixture](../../tests/fixtures/legacy_sqlite37/README.md).
Opening a live database never runs them.

This page explains what each numbered SQLite migration adds. It is an index to
the SQL, not a release or deployment history: applying a migration changes the
local database structure, but does not mean a dataset year was accepted, a
dataset release was published, or the migration was deployed to production.
For the live stage, see [project status](../status.md). For differences between
frozen application sources, see [candidate history](candidate-history.md).

## Version semantics

The port keeps two explicit versions. The **import schema version** describes
the frozen SQLite source and its exact `meta.schema_version` history; it stays 37. The **native schema version** describes PostgreSQL's applied migrations.
Its checked schema metadata and `ops.schema_identity()` advance together,
starting with native migration 38 for the stored `dryrun` identity. Updating
native metadata never rewrites the imported source version or migration 37.
A worker refuses a mismatched native version; only the explicit owner job
migrates it ([D-0276](../../journal/decisions/0276-version-native-schema-without-changing-imported-history.md)).

Native migration 39 changes four bulk history-fence triggers to counted
statement transitions. It preserves their per-row revision deltas and all
table contents. Native 38 remains readable through the explicit, read-only
verification checkpoint path with its exact prefix checksum; it remains
ineligible for an ordinary worker open
([D-0284](../../journal/decisions/0284-count-bulk-history-fence-changes-per-statement.md),
[D-0285](../../journal/decisions/0285-read-verified-native38-checkpoints-without-migrating-them.md)).

Native migration 40 batches pending-work enqueue and invalidation callbacks.
Each changed unit still advances its generation once, with retry fields,
missing-generation update behavior and exact history deltas preserved.
Publication and generation-insert fences remain per row
([D-0286](../../journal/decisions/0286-batch-pending-work-generation-updates.md)).

Native migration 41 indexes `subject_id` on `identity_links` and
`link_candidates`. Link replacement deletes by that field across subject
kinds; the existing composite keys lead with `subject_kind`. The new
nonunique indexes preserve the existing predicates, rows, history and write
order ([measured scans](../../journal/evidence/runtime/postgres-stage2-2026-11-17/link-subject-delete-plans.json)).

The SQLite schema version is the migration number recorded in both
`PRAGMA user_version` and the `schema_version` row in `meta`. A writable
`open_database()` call applies each intervening numbered migration in order,
in an individual transaction, and records the version in both places. A
read-only open does not migrate. Production migrations use the reviewed
maintenance procedure under hold; see [operations](operations.md). The
schema is cumulative: a database at version N retains the changes from all
earlier migrations. This number is independent of dataset release IDs, history
year acceptance, and publication state.

Production reached schema 29 under the operator hold on 2026-09-17. The guarded
migration preserved all 116 predecessor application tables and added only the
one-row dispatch fence. Production input acceptance, ordinary work and dataset
publication were separate gates. The exact candidate-006 input bundle has since
been accepted under the unchanged hold; ordinary work and publication remain
pending. See [project status](../status.md) and the
[independent audit](../../journal/evidence/runtime/held-schema29-migration-2026-09-17/postmigration-review-001/receipt.json).
