# SQLite schema history

This page explains what each numbered SQLite migration adds. It is an index to
the SQL, not a release or deployment history: applying a migration changes the
local database structure, but does not mean a dataset year was accepted, a
dataset release was published, or the migration was deployed to production.
For the live stage, see [project status](../status.md). For differences between
frozen application sources, see [candidate history](candidate-history.md).

## Version semantics

The SQLite schema version is the migration number recorded in both
`PRAGMA user_version` and the `schema_version` row in `meta`. A writable
`open_database()` call applies each intervening numbered migration in order,
in an individual transaction, and records the version in both places. A
read-only open does not migrate. Production migrations use the reviewed
maintenance procedure under hold; see [operations](operations.md). The
schema is cumulative: a database at version N retains the changes from all
earlier migrations. This number is independent of dataset release IDs, history
year acceptance, and publication state.

Production reached schema 29 under the operator hold on 2026-09-17. The guarded
migration preserved all 116 predecessor application tables and added only the
one-row dispatch fence. Production input acceptance, ordinary work and dataset
publication were separate gates. The exact candidate-006 input bundle has since
been accepted under the unchanged hold; ordinary work and publication remain
pending. See [project status](../status.md) and the
[independent audit](../../journal/evidence/runtime/held-schema29-migration-2026-09-17/postmigration-review-001/receipt.json).
