# Why the next release loses 19 result events, WDR, and most event cities

Date: 2026-10-12 (UTC), production read around 14:00 UTC  
Type: Investigation  
Topic: Release support  
Related plan or decision: D-0022, D-0224, D-0225, D-0241; [four events lost release support](four-events-lost-release-support-2026-10-11.md)

## Summary

1. One cause explains almost every loss from `138352e` to `cand_1f2393abae394fdf`. An event's header row (`events`) now cites a WSDC calendar capture taken after the baseline. Calendar pages have no admission contract, so the row is "legacy" and may publish only if it equals the baseline row. It does not, so the builder withholds the whole event partition, accepted results included.
2. 308 baseline events are withheld this way. 19 carry results: 2,736 placements, 10,679 entries, 320 contests. This includes all 13 events with WDR results; the 9 with source `wdr` are why that source shows 0 events.
3. None of it is transient. The losses began with the first build after the baseline (2026-09-24, closure mode), before phases 3 to 5. All 1,129 withheld partitions are `source_support_unavailable`, none `units_not_current`. The project re-run has drained. A re-extraction on current state still withholds all 308.
4. The metadata, registry-link and coverage drops follow from the same 308 events, except 4 events that lost a city and 1,619 empty coverage rows that only the closure builder wrote.
5. The owner's `events 2105->1805` row covers these events by count. The text it was approved on never said that 19 of them carry results.

## Findings

**One event end to end: Florida Dance Magic 2026.**

- Results: WDR watch `41fd58c8f7883fb0` (`wdr.rounds`), snapshot `snap_20260909T150700Z_9daf9b317bf0`. The accepted generation `gen_6fd27e81…` is contract 5 (2026-10-09). It has 41 `round_sheet` observations at parser 4.
- Project rows: `project/event` holds 26 contests, 32 rounds, 709 entries and 230 placements. `link/event` is current. `source_event_map` maps `wdr:e9a42d05…` to the event by override. The `project/source_event/wdr:*` scopes hold 0 rows.
- Header: in the baseline, the header row was the WDR override row (`snapshot_id=override`, `source=wdr`, 07-01 to 07-31), which needs no support. The inventory and resolution generations now emit a calendar row instead. That row cites `snap_20260922T200623Z_5050a63dd30c_1b14c571cd6a`, a Wayback copy of `worldsdc.com/events/` fetched 2026-09-22. It has the real dates (07-23 to 07-26) and the website.
- Support: no `wsdc_calendar.events` generation is accepted, because `admission_policies` lists it as `shadow:unassessed` and `admission/contracts.py:34-68` gives it no contract. So `SupportIndex` returns `legacy_unassessed`. `_legacy_matches` (`build/closure_rows.py:109-142`) then compares the row to the baseline, ignoring only processing and owner columns, so `snapshot_id`, `source`, `sources`, the dates and `website` all count. The row fails.
- Partition: `build/partitions.py:791-807` rejects both header rows, and `_close` (`:852-868`) withholds `event/2026-07-florida-dance-magic` (`legacy_owned_values_not_published: 2`). The D-0022 exception at `:859` keeps the event only when another generation supplies an `events` row, and the results generation supplies none.
- Candidate: the event and its results are absent.

**What changed and when.** The 19 are in every candidate up to the baseline and in none from `cand_8e0884ccdbc44935` (2026-09-24 21:32, closure mode, 1,796 events) on. Calendar captures arrived on 2026-09-21 at 22:04 (one origin capture) and on 2026-09-22 (16 Wayback captures). The closure path applies the same rule (`closure_rows.py:424-444`). Phases 3 to 5 and the H17 deploy did not cause this.

**Diff of the rejected rows.** 217 of the 308 events differ only in labels: `snapshot_id`, `parser_version`, `sources` and `history_source`. 9 of these carry results, with 960 placements, 147 cities and 6,900 registry links. The other 91 have changed facts, mostly better dates and a website; 10 of these carry results (1,776 placements). Every rejected row is an `events` row; no results row was rejected.

**The approval.** All 308 events missing now were also missing from `cand_f4e085b218264fec`, the build measured for the row `events,2105,1805`. The row is a floor on the count, so the gate accepts these losses. `docs/plans/architecture.md` describes the withheld partitions as "legacy rows the baseline did not publish", but each of the 308 was published. The receipt (`architecture-phase34-2026-10-05`) checked no per-event results. `events_with_placements` rose from 107 to 227, so the 19 lost result events were hidden by gains.

**No partitioned-assembly column defect.** The candidate's `events` schema carries city, region, country and website. Only 4 present events lost a value. For Finnfest, no current calendar generation holds a row (checked through `derivation_row_refs`), and the scoring.dance inventory row has `city=None`.

## Conclusion and follow-up

Nothing comes back on its own: about 0% of these losses will return without a change. Recommended fixes, in order:

1. **Baseline header fallback (build scope only).** In `build/partitions.py` (`extract`/`_close`, the D-0022 branch near `:852-868`), when a legacy `events` row is rejected and the baseline holds that event, publish the baseline row instead of withholding the partition. Mirror this in `closure_rows.py`. This restores all 308 events, the 19 result events, 13,086 registry links, 160 cities, 241 start dates and 230 websites. It publishes only values already published. `build/partitions.py` and `closure_rows.py` are in the build scope only, not in any project or link scope, so no project units re-run. The first build rebuilds every partition, because `partition_modules` changes (about 526 s cold on 2026-10-05). Two catches: it changes the D-0224 publication rule, so it needs a decision record; and 10 result events keep the baseline's month-wide dates labelled `day`. Another subagent is editing `build/` now, so coordinate with it.
2. **Re-admit the 309 `scoringdance.event` units** whose observations still carry parser 3 (D-0241). This is an operating action, not code. It makes 41 events (6 with results) accepted with their current `sources`.
3. **Review a contract for `wsdc_calendar.events`** (and possibly the newsletter and swingdancecouncil listings). Calendar rows would then publish their corrected dates and websites. `admission/contracts.py` sits in all 9 project scopes, the link and build scopes and 30 parse or extract scopes, so this is a full re-run (about 36k project units). Batch it with maintenance item 20. It also needs a source-policy decision.
4. **Make the gate check result events one by one** (`publish/gate.py`): refuse when an event that had placements in the baseline is gone, so a net count can't hide it. Correct the "did not publish" sentence in `architecture.md`.
5. Low priority: the 4 events whose city now comes only from a scoring.dance or EEPro row. The scoring.dance list JSON carries `city`; mapping it is a project-scope change. The empty coverage rows need no fix.

## Evidence and reproduction

The read-only scripts `a1.py` to `a20.py` and the output `a7.json` stayed in the session scratch directory (`scratchpad/losses/`, not retained). They read `state.sqlite` with `mode=ro` and the candidate parquet files, and replay `partitions.select` and `extract` with the deployed code. Each replay used a temporary baseline spool under the worker's `/tmp`. No production state was written.
